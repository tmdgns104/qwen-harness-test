# HC-005 - Exact and Hash Invariant Checks

## Status

APPROVED - READY FOR CONTRACT BASELINE

## Parent

ADR-001 - Deterministic Harness Core Before Further Orchestration

## Problem

A successful verification command does not prove that a required file has exactly the expected content. Qwen self-report also cannot be trusted as completion Evidence.

Tasks may define deterministic invariants such as exact file content or an expected SHA-256 hash. The Harness needs a small independent mechanism that compares those requirements with the actual Repository file.

## Goal

Provide deterministic checks for exact file content and SHA-256 file hashes and return objective structured results that later Harness stages can consume.

## Responsibility Boundary

HC-005 is limited to deterministic inspection of explicitly supplied exact-content and SHA-256 invariants.

HC-005 does not:

- parse Markdown Task syntax for invariant declarations;
- decide Allowed Changes or Forbidden Changes;
- inspect Git baselines or changed paths;
- execute verification commands;
- assemble final Evidence across Harness stages;
- produce the final Task PASS, FAIL, or BLOCKED decision;
- invoke an LLM, Worker backend, OpenCode, Ollama, or Codex;
- retry or repair Repository content.

Invariant requirements must already be supplied explicitly to HC-005 by a caller or later contract layer. HC-005 only measures the actual Repository state against those supplied requirements.

## Public Contract

HC-005 will expose two read-only deterministic checks.

### Exact Content Check

A frozen result object will represent:

- Repository-relative `path`;
- `expected_content` supplied by the caller;
- whether the file `exists`;
- whether the actual file content `matches` exactly.

The exact-content check compares the file bytes with `expected_content.encode("utf-8")`. No newline normalization, whitespace trimming, case folding, or semantic interpretation is allowed.

A missing file is represented as `exists=False` and `matches=False`; it is not treated as a successful invariant.

### SHA-256 Check

A frozen result object will represent:

- Repository-relative `path`;
- caller-supplied `expected_sha256`;
- computed `actual_sha256` when the file exists;
- whether the file `exists`;
- whether the digest `matches`.

SHA-256 is calculated from the file bytes. The expected digest must contain exactly 64 hexadecimal characters. Invalid digest syntax raises `ValueError` before file inspection. Hexadecimal letter case does not change digest equality.

A missing file is represented as `exists=False`, `actual_sha256=None`, and `matches=False`.

### Path Boundary

HC-005 accepts Repository-relative paths that have already been supplied and authorized by the caller. It does not perform Allowed/Forbidden scope decisions or invent paths. The target path is resolved before inspection. Files are inspected read-only only when the resolved target remains beneath the supplied Repository root; a resolved path that escapes the Repository root is rejected.

## API Contract

HC-005 will add the following frozen result types and functions to `tools/harness_core.py`:

- `ExactContentResult(path: str, expected_content: str, exists: bool, matches: bool)`
- `Sha256Result(path: str, expected_sha256: str, actual_sha256: str | None, exists: bool, matches: bool)`
- `check_exact_content(repo_root: str, path: str, expected_content: str) -> ExactContentResult`
- `check_sha256(repo_root: str, path: str, expected_sha256: str) -> Sha256Result`

## Failure Semantics

- `path` must be Repository-relative and must resolve beneath `repo_root`.
- Absolute paths or paths that escape `repo_root` raise `ValueError` before file inspection.
- An invalid SHA-256 expectation raises `ValueError` before file inspection.
- A missing target file is objective mismatch Evidence, not an exception.
- A target that exists but is not a regular file raises `ValueError`.
- An unexpected file-reading or hashing OS failure raises `RuntimeError`.
- HC-005 never modifies Repository content.

## Acceptance Criteria

Objective tests must demonstrate at minimum:

1. exact UTF-8 content match returns `exists=True` and `matches=True`;
2. exact content mismatch returns `exists=True` and `matches=False`;
3. newline or whitespace differences are not normalized;
4. missing exact-content target returns `exists=False` and `matches=False`;
5. SHA-256 match returns the actual digest and `matches=True`;
6. SHA-256 mismatch returns the actual digest and `matches=False`;
7. hexadecimal case in an otherwise valid expected SHA-256 digest is accepted;
8. malformed SHA-256 expectations fail before file inspection;
9. missing hash target returns `exists=False`, `actual_sha256=None`, and `matches=False`;
10. absolute or Repository-escaping paths fail closed;
11. non-file targets fail closed;
12. result objects are frozen;
13. existing HC-001 through HC-004 behavior remains unchanged.
14. unexpected file-reading or hashing OS failures are translated to `RuntimeError`.
