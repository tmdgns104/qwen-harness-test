# HC-007 - Deterministic Final Gate

## Status

APPROVED - READY FOR CONTRACT BASELINE

## Parent

ADR-001 - Deterministic Harness Core Before Further Orchestration

## Problem

HC-006 can assemble immutable objective Harness Evidence, but the Harness Core still lacks the final deterministic decision that converts mechanically checkable Evidence into an authoritative PASS or FAIL result. LLM or Worker self-reported PASS must not override deterministic failure Evidence.

## Goal

Evaluate an HC-006 `HarnessEvidence` object using only mechanically decidable conditions and return one immutable deterministic PASS/FAIL gate result without LLM reasoning, retry policy, Worker execution, or orchestration.

## Responsibility Boundary

HC-007 is limited to evaluating an already-assembled HC-006 `HarnessEvidence` object. It does not collect, repair, rerun, or reinterpret earlier-stage Evidence.

HC-007 does not:

- parse Task Markdown;
- query Git or recalculate changed paths;
- execute verification commands;
- read Repository files or recalculate hashes;
- retry Worker work;
- produce `BLOCKED` orchestration state;
- invoke an LLM, Worker backend, OpenCode, Ollama, or Codex;
- modify Repository content;
- automatically advance to another Task.

## Public Contract

HC-007 will add one frozen result type and one deterministic gate function to `tools/harness_core.py`.

### FinalGateResult

`FinalGateResult(passed: bool, failures: tuple[str, ...])`

`failures` contains zero or more deterministic failure-category strings in the fixed order defined by this contract. A PASS result has `passed=True` and `failures=()`.

### Final Gate Function

`evaluate_final_gate(evidence: HarnessEvidence) -> FinalGateResult`

The gate evaluates these categories in this fixed order:

1. `evidence_consistency`
2. `scope`
3. `verification`
4. `exact_content`
5. `sha256`

Each category appears at most once in `failures`.

## Deterministic Gate Rules

### Evidence consistency

Add `evidence_consistency` when any of the following is true:

- `evidence.path_scope_results` is not exactly equal to the tuple obtained by applying the existing HC-002 `is_path_allowed(path, evidence.scope)` function to every `evidence.changed_paths` item in supplied order; this comparison includes path values, allowed booleans, length, order, and duplicates;
- an exact-content result has `matches=True` while `exists=False`;
- a SHA-256 result has `matches=True` while `exists=False`;
- a SHA-256 result has `matches=True` while `actual_sha256 is None`;\n- a SHA-256 result has `matches=True` while its non-None `actual_sha256` does not equal `expected_sha256` case-insensitively.

HC-007 does not otherwise duplicate validation already owned by HC-001 through HC-006.

### Scope

Add `scope` when any deterministically recomputed HC-002 scope result for `evidence.changed_paths` is `False`. The same recomputed scope facts used for Evidence consistency must be reused rather than independently implementing path-matching logic.

### Verification

Add `verification` when any `VerificationCommandResult.exit_code` is non-zero.

### Exact content

Add `exact_content` when any `ExactContentResult.matches` value is `False`.

### SHA-256

Add `sha256` when any `Sha256Result.matches` value is `False`.

After all categories are evaluated, return `passed=True` only when `failures` is empty. Otherwise return `passed=False`.

Empty changed-path, verification, exact-content, or SHA-256 result tuples do not fail merely because they are empty. HC-007 must not infer requirements that are absent from the supplied Evidence.

## Failure Semantics

Negative Evidence is a normal gate input, not an exception condition. HC-007 must evaluate all contracted categories and return one complete deterministic result rather than stopping after the first failure.

- a deterministically recomputed HC-002 scope result with `allowed=False` produces the `scope` failure category.
- a non-zero verification exit code produces the `verification` failure category.
- `matches=False` produces the corresponding invariant failure category.
- the specifically contracted impossible or mismatched Evidence relationships produce `evidence_consistency`.
- multiple failures are collected in the fixed contract order.
- the same category is never duplicated even when multiple Evidence items fail within that category.
- HC-007 does not silently repair malformed or inconsistent Evidence.
- HC-007 does not convert mechanically negative Evidence into `BLOCKED`.
- HC-007 performs only the consistency checks explicitly defined in this Task and does not reimplement earlier-stage collection or validation logic.

## Acceptance Criteria

Objective tests must demonstrate at minimum:

1. `FinalGateResult` is a frozen dataclass with exactly `passed` and `failures` fields;
2. completely positive Evidence returns `FinalGateResult(passed=True, failures=())`;
3. a forbidden or otherwise disallowed changed path returns `passed=False` with `scope`;
4. one or more non-zero verification exit codes return `passed=False` with one `verification` category;
5. an exact-content mismatch returns `passed=False` with `exact_content`;
6. a SHA-256 mismatch returns `passed=False` with `sha256`;
7. multiple simultaneous failures are returned once each in the fixed order `evidence_consistency`, `scope`, `verification`, `exact_content`, `sha256`;
8. any mismatch between `path_scope_results` and HC-002 recomputed scope facts, including path, allowed boolean, order, length, or duplicate structure, produces `evidence_consistency`;
9. `ExactContentResult(matches=True, exists=False)` produces `evidence_consistency`;
10. `Sha256Result(matches=True, exists=False)` produces `evidence_consistency`;
11. `Sha256Result(matches=True, actual_sha256=None)` produces `evidence_consistency`;\n12. `Sha256Result(matches=True)` with non-None actual and expected digests that differ case-insensitively produces `evidence_consistency`;
13. empty changed-path and optional result tuples can PASS when no other deterministic failure exists;
14. negative Evidence is returned as a gate result rather than raised as an exception;
15. final-gate evaluation performs no Git query, process execution, Repository file read, hash calculation, LLM call, Worker execution, retry, or Repository modification;
16. existing HC-001 through HC-006 behavior remains unchanged and the full Harness Core test suite passes.
