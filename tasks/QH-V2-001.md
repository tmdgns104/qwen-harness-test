# QH-V2-001 - Slim Task Worker

## Status

`APPROVED - READY FOR IMPLEMENTATION`

## Goal

Simplify the Qwen task-worker so it focuses only on implementing one explicitly assigned Task.

Reduce prompt size, unnecessary reasoning, repeated tool calls, and responsibilities that should be handled by deterministic verification.

## Problem

Harness V1 showed these failures in real repository work:

- absolute repository path hallucination or misspelling;
- repeated exact-string edit failures;
- malformed edit tool arguments;
- requirements invented outside the assigned Task;
- step-budget exhaustion;
- slow execution caused by excessive Worker responsibilities.

## Scope

Change only the global OpenCode `task-worker` agent definition.

The Worker must:

1. read exactly one explicitly assigned Task;
2. use repository-relative paths;
3. read only files needed for implementation;
4. modify only Task-allowed files;
5. implement the requested change;
6. report changed files and implementation result;
7. stop.

## Worker Responsibilities

The Worker is responsible for:

- Task interpretation;
- implementation;
- Task scope compliance;
- basic implementation-time error reporting.

## Responsibilities Removed from Worker

The Worker is NOT responsible for:

- full Git verification;
- Git baseline comparison;
- checking every protected file;
- independent final verification;
- Human Gate decisions;
- selecting the next Task;
- determining project status;
- running tests unless the assigned Task explicitly requires them during implementation.

These responsibilities belong to later Evidence Collector / Verifier stages.

## Path Rules

- Treat the OpenCode working directory as repository root.
- Use repository-relative paths for repository files.
- Do not reconstruct absolute repository paths from memory.
- Do not alter or invent directory names.
- Example:
  - use `DECISIONS.md`
  - not `D:\...\DECISIONS.md`

## Task Fidelity Rules

- The assigned Task is the only source of implementation requirements.
- Do not invent metrics, tests, ADR contents, policies, dependencies, or workflow requirements.
- Do not start another Task.
- Do not modify the Task specification itself unless explicitly allowed.

## File Modification Rules

- Read a target file before modifying it.
- Prefer patch-style modification for long Markdown, append operations, and multi-line edits when available.
- Use exact-string edit only when the exact short old text was directly observed.
- Do not repeatedly retry guessed `oldString` values.
- If the same modification fails twice using reasonable strategies, stop and report `BLOCKED`.

## Step Budget

Use a small bounded step budget.

Target:

`steps: 12`

Do not increase the budget merely to compensate for repeated tool failures.

## Allowed Change

- `C:\Users\user\.config\opencode\agents\task-worker.md`

## Forbidden Changes

- Personal Engineering Brain repository
- `repo-analyzer.md`
- `task-verifier.md`
- OpenCode commands
- model configuration
- LangGraph
- LangChain
- application code

## Acceptance Criteria

- Worker prompt is materially shorter than Harness V1.
- Worker uses repository-relative paths by policy.
- Worker has no responsibility for independent final verification.
- Worker has no responsibility for Git baseline/protected-file verification.
- Worker does not select or start another Task.
- Worker does not invent requirements outside the assigned Task.
- Worker has explicit protection against repeated exact-edit failure loops.
- `steps` is 12.
- No other Harness component is changed.
