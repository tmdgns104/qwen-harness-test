This Task implements the final Milestone 1 stage:

End-to-End regression with a real small Repository Task.

## Problem

The Worker Adapter, Repository tools, Single-Task Runner, bounded Retry layer,
and Worker-facing CLI have each been verified independently.

The complete production path has not yet been verified as one real flow:

Human CLI
-> bounded Retry
-> Single-Task Runner
-> native Ollama API
-> Qwen3:8B
-> backend-neutral tool call
-> Harness-owned Repository read/write tool
-> Git/Test Evidence
-> Human-controlled qh close

Milestone 1 is not complete until this real path succeeds against a small,
deterministic Repository Task.

## Goal

Use the real approved Worker path to make one small deterministic edit to:

`target.txt`

The Worker must use Repository information rather than receiving the target
file's current value in this Task contract.

No Harness implementation code is added in this Task.

## Real Worker Configuration

Use the existing default Worker path unchanged:

Deterministic Python Harness
-> native Ollama API
-> Qwen3:8B

Use the existing fast path:

`think:false`

Do not switch models or introduce a higher-reasoning fallback in this Task.

## Required Worker Execution

Execute through the real user-facing command:

`python tools\qh.py run QH-V2-E2E-001`

Do not bypass qh run by manually calling:

- Ollama;
- OllamaToolSession;
- run_single_task;
- run_with_retry;
- repo_tools.

The purpose of this Task is to verify the complete approved user path.

## Required Repository Change

The Worker must:

1. read `target.txt`;
2. use the file's actual current text as input;
3. remove trailing CR/LF line endings from that read value only;
4. write `target.txt` as:

`E2E-RESULT:<ORIGINAL>`

followed by exactly one newline.

`<ORIGINAL>` means the value obtained from the Repository read.

The current value of target.txt is intentionally not specified in this Task.

Do not infer or invent `<ORIGINAL>`.

The Worker must obtain it from the Repository.

## Expected Evidence

For the current baseline fixture, successful execution will be objectively
verified as:

`target.txt` -> `E2E-RESULT:BEFORE\n`

This expected value is Verification evidence and is not Worker authority.

Qwen self-reported PASS is not accepted as Evidence.

## Worker Tool Boundary

The Worker may receive only the existing Milestone 1 tools:

- `read_repo_text`
- `write_repo_text`

The Worker must not receive:

- shell;
- Git;
- Verification;
- Evidence;
- Final Gate;
- commit;
- Task lifecycle;
- Architecture operations.

## Retry Boundary

Existing ADR-009 behavior remains unchanged.

- maximum two Runner attempts;
- retry only transient Worker/session failure;
- no whole-Runner retry after Repository write attempt;
- SAFETY -> FAIL;
- STEP_BUDGET -> FAIL;
- exhausted or unsafe transient -> BLOCKED.

This Task does not tune retry behavior.

## CLI Outcome Boundary

`qh run` may produce:

- NORMAL
- FAIL
- BLOCKED

Only NORMAL is a successful Worker interaction.

NORMAL is still not Repository Task PASS.

Worker output such as `PASS` remains non-authoritative.

## Human Gate

After qh run:

1. inspect the CLI outcome;
2. inspect Git diff;
3. verify only the allowed target change occurred;
4. commit the Worker-produced change;
5. invoke qh close with that explicit HEAD;
6. accept completion only if full Verification and Final Gate PASS.

No automatic commit or Task completion is permitted.

## E2E Success Criteria

The E2E run succeeds only if all of the following are true:

1. `qh run QH-V2-E2E-001` uses the real Worker path.
2. The final CLI Outcome is NORMAL.
3. At most two Runner attempts are consumed.
4. No write side-effect warning remains unresolved.
5. `target.txt` becomes exactly `E2E-RESULT:BEFORE\n`.
6. No forbidden fixture file changes.
7. No Harness implementation file changes.
8. No test implementation file changes.
9. Qwen self-report is not used as PASS Evidence.
10. Git Scope Evidence is clean.
11. full Task Verification passes.
12. Final Gate passes.
13. completion remains Human-controlled through qh close.

## Failure Interpretation

### FAIL

If the CLI returns deterministic FAIL:

- do not manually repair target.txt;
- inspect structured failure classification;
- diagnose within current Architecture;
- do not broaden Worker authority.

### BLOCKED

If the CLI returns BLOCKED:

- do not blindly rerun;
- inspect attempts and write-side-effect risk;
- preserve Repository state for diagnosis;
- do not manually force PASS.

### NORMAL With Wrong Repository Result

If qh run reports NORMAL but target.txt is wrong:

- treat the Task as failed;
- Qwen terminal output is not authoritative;
- do not close;
- diagnose semantic/tool behavior using Git Evidence.

## No Manual Success Substitution

The Human must not manually edit target.txt to create the expected result after
a failed real Worker execution and then claim E2E PASS.

A successful E2E result must be produced by the real qh run Worker path.

## Performance

No duplicate manual full Verification is required before qh close.

During diagnosis, focused checks are permitted.

The final qh close remains authoritative and executes the full Verification
contract once.

## Stop Conditions

STOP and report before continuing if:

- `qh run` cannot reach native Ollama;
- Qwen3:8B is unavailable;
- Worker requests an unauthorized tool;
- Worker requests multiple tools in one step;
- Worker tries to modify a lifecycle-control path;
- Worker tries to modify a forbidden or out-of-scope path;
- Retry returns BLOCKED;
- deterministic SAFETY or STEP_BUDGET FAIL occurs;
- target.txt result is semantically wrong after NORMAL;
- any forbidden file changes;
- Harness implementation modification appears necessary;
- retry/model/tool/Architecture changes appear necessary;
- qh close does not parse the full Verification contract.

After successful completion, proceed to the separately planned
Post-Milestone 1 Hardening & UX Improvement review.
