# HC-006 - Evidence Assembly

## Status

COMPLETE - VERIFIED - commit 3f869c3

## Parent

ADR-001 - Deterministic Harness Core Before Further Orchestration

## Problem

HC-001 through HC-005 can produce deterministic scope, Git, verification-command, and invariant results, but those objective facts are still represented separately. A later deterministic Final Gate needs one stable Evidence object rather than reconstructing mechanically checkable facts through LLM reasoning.

## Goal

Assemble already-produced deterministic Harness results into one immutable structured Evidence object without producing a final PASS, FAIL, or BLOCKED decision.

## Responsibility Boundary

HC-006 is limited to assembling deterministic Evidence already available from earlier Harness Core stages and deriving per-changed-path scope facts by reusing the existing HC-002 `is_path_allowed()` decision function.

HC-006 does not:

- parse Task Markdown;
- capture a new Git baseline or query Git for changed paths;
- execute verification commands;
- read Repository files for exact-content checks or calculate hashes;
- invent, repair, retry, or modify Evidence supplied by earlier stages;
- write Evidence JSON or other result files;
- produce a final Task PASS, FAIL, or BLOCKED decision;
- invoke an LLM, Worker backend, OpenCode, Ollama, or Codex;
- modify Repository content.

For each supplied changed path, HC-006 may call the existing HC-002 `is_path_allowed(path, scope)` function and record that boolean fact. An `allowed=False`, non-zero verification exit code, or invariant mismatch remains Evidence only; HC-006 must not convert it into a final verdict.

## Public Contract

HC-006 will add two frozen result types and one assembly function to `tools/harness_core.py`.

### PathScopeEvidence

`PathScopeEvidence(path: str, allowed: bool)`

For every supplied changed path, HC-006 records the original Repository-relative path and the boolean result returned by the existing HC-002 `is_path_allowed(path, scope)` function.

### HarnessEvidence

`HarnessEvidence` contains:

- `scope: ChangeScope`
- `baseline: GitBaseline`
- `changed_paths: tuple[str, ...]`
- `path_scope_results: tuple[PathScopeEvidence, ...]`
- `verification_results: tuple[VerificationCommandResult, ...]`
- `exact_content_results: tuple[ExactContentResult, ...]`
- `sha256_results: tuple[Sha256Result, ...]`

The object is immutable. Earlier-stage result objects are preserved rather than converted into new semantic summaries.

### Assembly Function

`assemble_evidence(scope: ChangeScope, baseline: GitBaseline, changed_paths: tuple[str, ...], verification_results: tuple[VerificationCommandResult, ...] = (), exact_content_results: tuple[ExactContentResult, ...] = (), sha256_results: tuple[Sha256Result, ...] = ()) -> HarnessEvidence`

The function must:

1. preserve `scope` and `baseline` unchanged;
2. preserve supplied `changed_paths` exactly and in supplied order;
3. call `is_path_allowed(path, scope)` once for each supplied changed path and create one corresponding `PathScopeEvidence` in the same order;
4. preserve verification, exact-content, and SHA-256 result tuples exactly and in supplied order;
5. allow empty changed-path, verification, exact-content, or SHA-256 result tuples;
6. perform no Git, subprocess, Repository file-read, hash, LLM, or final-verdict operation.

HC-006 must not sort, deduplicate, discard, rewrite, or reinterpret supplied Evidence.

## Failure Semantics

HC-006 expects caller-supplied values that already satisfy the earlier HC-001 through HC-005 data contracts. It does not duplicate validation owned by those stages.

- HC-006 must not convert negative Evidence into an exception merely because a path is not allowed, a verification exit code is non-zero, or an invariant does not match.
- Exceptions raised by the existing HC-002 `is_path_allowed()` function are not silently repaired or converted into successful Evidence.
- HC-006 does not invent fallback Evidence when required assembly inputs are unavailable.
- Tuple contents and element order must be preserved. Python object identity of the tuple itself is not part of the contract.
- Duplicate changed paths or duplicate earlier-stage results, when explicitly supplied, remain present; HC-006 does not deduplicate them.

## Acceptance Criteria

Objective tests must demonstrate at minimum:

1. `PathScopeEvidence` is a frozen dataclass containing `path` and `allowed`;
2. `HarnessEvidence` is a frozen dataclass containing the contracted HC-001 through HC-005 Evidence fields;
3. `scope` and `baseline` are preserved in the assembled Evidence;
4. changed paths are preserved exactly in supplied order;
5. one `PathScopeEvidence` is created for every changed path in the same order;
6. allowed and forbidden changed paths are recorded as `allowed=True` and `allowed=False` without producing a final verdict;
7. duplicate changed paths are preserved rather than deduplicated;
8. verification results are preserved in supplied order, including non-zero exit codes;
9. exact-content results are preserved in supplied order, including mismatch Evidence;
10. SHA-256 results are preserved in supplied order, including mismatch Evidence;
11. empty changed-path and earlier-stage result tuples are accepted and represented as empty tuples;
12. `is_path_allowed()` is reused for per-path scope facts rather than reimplementing path matching inside HC-006;
13. assembly performs no Git query, verification execution, Repository file inspection, hash calculation, LLM call, or Repository modification;
14. existing HC-001 through HC-005 behavior remains unchanged.
