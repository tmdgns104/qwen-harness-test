# HC-004 - Verification Command Runner

## Status

COMPLETE - PARENT VERIFICATION PASSED

## Problem

Repository Tasks contain Verification sections, but their current Markdown forms are heterogeneous. Executable commands and descriptive verification instructions must not be conflated or interpreted through LLM judgment.

## Goal

Provide deterministic execution of explicitly approved verification commands and capture their actual exit results as objective Evidence.

HC-004 is decomposed before implementation into HC-004A and HC-004B.

## Decomposition

### HC-004A - Verification Command Contract Parser

Parse explicitly executable commands from the Task Verification contract. Ambiguous or unsupported command forms must fail closed rather than be guessed.

### HC-004B - Deterministic Verification Command Execution

Execute only commands supplied by the HC-004A contract and return structured command, exit code, stdout, and stderr results without using shell interpretation unless an approved later contract explicitly requires it.

## Responsibility Boundary

- HC-004 does not decide final Task PASS or FAIL.
- HC-004 does not perform changed-path scope evaluation.
- HC-004 does not assemble final Evidence.
- HC-004 does not invent verification commands.
- HC-004 does not execute descriptive prose from a Verification section.
- HC-004 does not invoke any LLM or Worker backend.

## Sequence

1. Complete HC-004A with objective tests.
2. Complete HC-004B with objective tests.
3. Verify the parent HC-004 contract.
4. Stop before HC-005.

## Parent Acceptance Criteria

- Explicit executable Verification commands are represented deterministically.
- Ambiguous Verification text cannot silently become an executable command.
- Approved commands execute with actual exit code, stdout, and stderr captured.
- Process-start failures fail closed.
- Existing HC-001 through HC-003 behavior remains unchanged.
- No LLM self-report can override command results.

## Verification

Run exactly:

`python -m unittest tests.test_harness_core`

Then verify actual changed paths against the Allowed Changes / Forbidden Changes contract.

## Allowed Changes

- `tools/harness_core.py`
- `tests/test_harness_core.py`
- `tasks/HC-004.md`
- `tasks/HC-004A.md`
- `tasks/HC-004B.md`
- `STATUS.md`

## Forbidden Changes

- `PROJECT.md`
- `REQUIREMENTS.md`
- `ARCHITECTURE.md`
- `DECISIONS.md`
- all unrelated Task files
- all fixture files unless separately approved

## Stop Condition

Stop after HC-004A and HC-004B are independently verified and the parent HC-004 Acceptance Criteria pass.

Do not start HC-005 automatically.
Do not implement Worker Adapter code.
