# HC-004A - Verification Command Contract Parser

## Status

APPROVED - READY FOR CONTRACT BASELINE

## Parent

HC-004 - Verification Command Runner

## Problem

The Repository contains heterogeneous `## Verification` Markdown. Executable commands must be distinguished from descriptive verification prose without LLM interpretation or command guessing.

## Goal

Parse explicitly marked executable verification commands into a deterministic immutable contract while failing closed on missing, empty, ambiguous, or unsupported Verification forms.

## Proposed Public Contract

Add a frozen dataclass:

`VerificationContract(commands: tuple[str, ...])`

Add a public parser:

`parse_verification_commands(markdown: str) -> VerificationContract`

The parser returns raw approved command strings in Repository-document order. It does not execute them.

## Supported Verification Syntax

Inside the `## Verification` section only, executable commands may be introduced by exactly one of these marker lines:

- `Run exactly:`
- `Run:`
- `Then run:`

Each marker must be followed by exactly one executable command represented as either:

- one standalone Markdown inline-code line containing the complete command; or
- one fenced code block containing exactly one non-empty command line.

Multiple explicit markers are allowed and command order must be preserved.

## Fail-Closed Rules

Raise `ValueError` when:

- the `## Verification` section is missing;
- no explicitly marked executable command exists;
- a supported marker is not followed by a supported command representation;
- a fenced block for a command contains more than one non-empty command line;
- command content is empty;
- descriptive prose, bullets, or backticked fragments are the only apparent verification instructions;
- an unsupported or ambiguous form would require guessing whether text is executable.

Do not infer commands from prose such as `verify changed paths`.
Do not treat `Verify with:` bullet lists as executable command contracts in HC-004A.

## Responsibility Boundary

- Parse only; do not execute subprocesses.
- Do not tokenize command strings into argv yet.
- Do not interpret shell operators.
- Do not perform scope checks.
- Do not assemble Evidence.
- Do not decide Task PASS or FAIL.
- Do not invoke an LLM or Worker backend.

## Required Tests

Tests must cover at minimum:

- HC-003 style `Run exactly:` plus inline-code command;
- HC-003B style `Run exactly:` plus fenced single-line command;
- QH-V2-MD-002 style `Run:` followed later by `Then run:` with command order preserved;
- prose after a valid command is not executed;
- `Verify with:` descriptive bullet form fails closed;
- missing Verification section fails;
- empty Verification section fails;
- marker without command fails;
- multi-command fenced block fails;
- frozen result cannot be mutated;
- existing HC-001 through HC-003 tests remain passing.

## Allowed Changes

- `tools/harness_core.py`
- `tests/test_harness_core.py`

## Forbidden Changes

- `PROJECT.md`
- `REQUIREMENTS.md`
- `ARCHITECTURE.md`
- `DECISIONS.md`
- `STATUS.md`
- `tasks/**`
- fixture files
- all other Repository files

## Acceptance Criteria

- `VerificationContract` is frozen and preserves command order.
- `parse_verification_commands()` supports only the explicit syntax defined above.
- Ambiguous Verification prose fails closed instead of becoming executable.
- The parser performs no command execution.
- Required focused tests pass.
- Full `python -m unittest tests.test_harness_core` passes.
- Existing HC-001 through HC-003 behavior is unchanged.
- Only the two Allowed implementation files change after the contract baseline.

## Verification

Run exactly:

`python -m unittest tests.test_harness_core`

Then verify actual changed paths against the Allowed Changes / Forbidden Changes contract.
